# 7.1 Authentication — Implementation Plan

## Requirement reference

- **SRS 7.1 Authentication** — "The system shall provide: Login, Logout, Password reset, Session management, Remember-me functionality, Account activation/deactivation."
- Optional future functionality (explicitly NOT required for V1.1): two-factor authentication, passkeys, SSO. The repo already enables 2FA + passkeys via Fortify config; they are left as-is.

## SRS references used

- SRS §7.1 (target requirement)
- SRS §69 Security Requirements — Authentication (secure password hashing)
- SRS §70 Multi-Tenant Data Isolation — auth pages are unauthenticated; no org data exposed
- SRS §NFR-005 Security — authentication, rate limiting
- V1.1 §0.26 idempotency — not applicable to interactive login/logout
- V1.1 §0.27 Security Hardening — session invalidation on sensitive account changes, secure sessions, rate limiting login
- V1.1 §0.29 Audit requirements — login success/failure as policy permits (not enforced for 7.1)
- V1.1 §0.37 Testing requirements — security tests

## Current-state findings

Requirement 7.1 is largely implemented already through Laravel Fortify + Inertia React pages:

| Capability | Status | Located in |
| --- | --- | --- |
| Login | Implemented | `FortifyServiceProvider::authenticateUsing`, `Auth/Login.jsx` |
| Logout | Implemented | Fortify `POST /logout`, `AppLayout.jsx` logout link |
| Password reset | Implemented | Fortify features, `Auth/ForgotPassword.jsx`, `Auth/ResetPassword.jsx`, `ResetUserPassword` |
| Email verification | Implemented (extra) | `MustVerifyEmail`, `Auth/VerifyEmail.jsx`, `verified` middleware |
| Session management | Implemented | `SessionController`, `Settings/Sessions.jsx`, `routes/web.php` |
| Remember-me | Implemented | `Auth/Login.jsx` remember checkbox → Fortify guard login |
| Account activation/deactivation | Implemented | `users.status`, `UpdateUser` action, `Settings/Users.jsx` |
| Inactive account login block | Implemented | `FortifyServiceProvider::authenticateUsing` |

### Gaps identified

1. **No automated test coverage** for any of the required auth capabilities. `tests/Feature` has no authentication suite (login, logout, password reset, sessions, remember-me, inactive-account block, registration→login consistency).
2. **Email normalization inconsistency**: Fortify lowercases the submitted username on login (`CanonicalizeUsername`, because `fortify.lowercase_usernames = true`), but `CreateNewUser` and `UpdateUserProfileInformation` store the email as typed. A user registered with a mixed-case email can never log in again because login always lowercases the lookup. Registration/profile must normalize to lowercase to keep login consistent.
3. **Session invalidation on password reset** missing: V1.1 §0.27 requires session invalidation on sensitive account changes; a reset password should terminate existing sessions for that account.

## Goals

- Satisfy SRS 7.1 for Login, Logout, Password reset, Session management, Remember-me, Account activation/deactivation.
- Make login robustly consistent with the Fortify lowercase-username convention.
- Invalidate existing sessions when a password is reset (security hardening).
- Provide automated negative + positive coverage for every required capability.

## Non-goals

- Two-factor authentication UI, passkeys UI, SSO (explicitly optional/future per SRS 7.1).
- Re-authentication prompts (V1.1 future hardening, out of scope for 7.1).
- Audit-logging login success/failure (policy permits omission; not a 7.1 requirement).
- Changing Fortify defaults, the login rate-limit strategy, or session driver.
- Email verification is a pre-existing complementary feature; not expanded.

## Implementation steps

1. Normalize email to lowercase on registration (`app/Actions/Fortify/CreateNewUser.php`).
2. Normalize email to lowercase on profile update (`app/Actions/Fortify/UpdateUserProfileInformation.php`).
3. Invalidate all sessions for the user in `app/Actions/Fortify/ResetUserPassword.php` after a successful reset, inside the broker transaction.
4. Add `tests/Feature/AuthenticationTest.php` covering all required capabilities.

## Database changes

None. The `users` table already has `status`, `remember_token`, `last_login_at`, `ulid`.

## Domain/application changes

Small, contained: email normalization in Fortify create/update actions, session cleanup in the password-reset action. No new actions/services; existing boundaries preserved.

## UI changes

None required. Login, register, forgot-password, reset-password, verify-email, 2FA challenge, confirm-password, and sessions pages already exist.

## Authorization/security changes

- Inactive accounts cannot authenticate (existing, now tested).
- Password reset invalidates the user's existing sessions.
- Sessions routed through the controller remain scoped to the authenticated user (`WHERE user_id = ...`).

## Tests to add or update

New `tests/Feature/AuthenticationTest.php` (factories per `.ai/rules/tests.md`):

- Login page renders.
- Unauthenticated access to `/dashboard` and `/settings/sessions` redirects to login.
- Correct credentials authenticate and redirect to `/dashboard`.
- Invalid credentials are rejected with errors; user stays a guest.
- Inactive account cannot log in (negative).
- Mixed-case registration stores lowercase email and lowercase login succeeds.
- Remember-me login writes `remember_token`.
- Logout ends the authenticated session.
- Forgot-password sends a `PasswordReset` notification for a known email.
- Password reset with a valid broker token replaces the password; new password logs in, old password fails.
- Password reset deletes existing sessions for the user.
- Sessions page lists the user's sessions.
- Signing out the current session is blocked.
- Signing out another session removes only that row.
- A user cannot sign out another user's session (isolation).

## Acceptance checklist

- [x] Login works and correctly rejects bad credentials and inactive accounts.
- [x] Logout terminates the session.
- [x] Password reset flow works end-to-end (link → reset → new password usable).
- [x] Password reset invalidates existing sessions.
- [x] Session management lists sessions and allows sign-out of other sessions only.
- [x] Users cannot act on another user's session.
- [x] Remember-me sets a persistent login cookie.
- [x] Registration/profile emails are normalized lowercase so login is consistent.
- [x] Negative cases are automated and pass.
- [x] No regressions in user management deactivation tests.

## Risks/ambiguities

- **Email casing**: Dev/test emails are lowercase; normalizing at registration is a strict improvement and matches Fortify's documented intent. Existing mixed-case dev rows would need manual cleanup, acceptable for a portfolio app.
- **Session driver in tests**: `phpunit.xml` uses `SESSION_DRIVER=array`, so session-management tests seed the `sessions` table directly and assert on it; the controller already reads/writes that table.
- **Scope discipline**: 2FA/passkeys/SSO are explicitly optional; no work beyond existing config was performed.
